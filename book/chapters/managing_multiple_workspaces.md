# Managing Multiple Workspaces

<details open>
<summary>Working with multiple ROS 2 workspaces and changing search priorities</summary>
</details>

Once you're comfortable with a single workspace overlaying ROS 2, you'll eventually want to work with multiple custom workspaces. Maybe you want to experiment with a modified version of Nav2 without affecting your main robot code. Or you're developing a reusable package separately from your robot-specific code. Or you want to test two different navigation algorithms and switch between them easily.

This chapter shows you how to chain multiple workspaces, change their search order, and manage complex workspace scenarios without creating an environment mess.

## Why Multiple Workspaces?

Here are common scenarios where multiple workspaces make sense:

**Scenario 1: Stable vs. Experimental**
- `~/robot_ws` — Your stable robot code
- `~/experimental_ws` — Testing new features without breaking your robot

**Scenario 2: Reusable vs. Robot-Specific**
- `~/common_ws` — Reusable packages you might use across multiple robots
- `~/my_robot_ws` — Robot-specific code that uses the common packages

**Scenario 3: Testing Alternative Implementations**
- `~/robot_ws` — Your main robot code
- `~/nav2_custom_ws` — Modified Nav2 packages
- Want to switch between system Nav2, your custom Nav2, depending on test

**Scenario 4: Modular Development**
- `~/sensors_ws` — Sensor drivers and processing
- `~/navigation_ws` — Navigation stack customizations
- `~/behaviors_ws` — High-level behavior code
- Each can be developed and tested independently

The key to managing these scenarios is understanding **workspace chaining**.

## Building One Workspace on Top of Another

The fundamental pattern is: **Source workspace A, then build workspace B.**

When you do this, workspace B records workspace A as its underlay (in addition to any underlay A already had). Let's work through a concrete example.

### Example: Creating a Common + Robot Workspace Setup

Start with a fresh terminal and create the common workspace:

```bash
# Terminal 1: Build common workspace
mkdir -p ~/common_ws/src
cd ~/common_ws/src

# Create a package with reusable utilities
ros2 pkg create common_utilities --build-type ament_python
# ... add your code ...

cd ~/common_ws
source /opt/ros/jazzy/setup.bash  # Underlay for common_ws
colcon build --symlink-install
```

Now `~/common_ws` is built with `/opt/ros/jazzy` as its underlay. Its `install/setup.bash` will source `/opt/ros/jazzy` automatically.

Next, create your robot-specific workspace that depends on `common_ws`:

```bash
# Terminal 2: Build robot workspace
mkdir -p ~/my_robot_ws/src
cd ~/my_robot_ws/src

# Create robot package that uses common_utilities
ros2 pkg create my_robot_bringup --build-type ament_python --dependencies common_utilities
# ... add your code ...

cd ~/my_robot_ws
source ~/common_ws/install/setup.bash  # ← This is the key!
colcon build --symlink-install
```

**What just happened**:
- Before building `my_robot_ws`, you sourced `common_ws`
- This made `AMENT_PREFIX_PATH` = `~/common_ws/install:/opt/ros/jazzy`
- When `colcon build` ran, it recorded **both** of those as underlays
- Now `my_robot_ws/install/setup.bash` will source `common_ws`, which sources `jazzy`

The chain is:

```mermaid
flowchart LR
    A[/opt/ros/jazzy] --> B[~/common_ws]
    B --> C[~/my_robot_ws]
    
    style C fill:#90EE90,stroke:#006400
    style B fill:#FFE4B5,stroke:#FF8C00
    style A fill:#E0E0E0,stroke:#808080
```

Now in a **new terminal** (always start fresh for running):

```bash
# Terminal 3: Run your robot
source ~/my_robot_ws/install/setup.bash
echo $AMENT_PREFIX_PATH
```

You'll see:
```
/home/user/my_robot_ws/install:/home/user/common_ws/install:/opt/ros/jazzy
```

The search order is:
1. `my_robot_ws` ← Searched first (highest priority)
2. `common_ws` ← Searched second
3. `/opt/ros/jazzy` ← Searched last (lowest priority)

This means:
- If a package exists in `my_robot_ws`, that version is used
- Otherwise, if it exists in `common_ws`, that version is used  
- Otherwise, if it exists in `/opt/ros/jazzy`, that version is used
- Otherwise, package not found error

<details>
<summary><strong>Deep Dive: The Dependency Chain in setup.bash</strong></summary>

If you look at `~/my_robot_ws/install/setup.bash`, you'll see something like:

```bash
# Source underlays (generated by colcon at build time)
source "/home/user/common_ws/install/setup.bash"

# Then add this workspace to paths
# ... prepend my_robot_ws to AMENT_PREFIX_PATH, etc. ...
```

And if you look at `~/common_ws/install/setup.bash`:

```bash
# Source underlays
source "/opt/ros/jazzy/setup.bash"

# Then add this workspace
# ... prepend common_ws to paths ...
```

So when you `source ~/my_robot_ws/install/setup.bash`, it:
1. Runs `source ~/common_ws/install/setup.bash`
   - Which runs `source /opt/ros/jazzy/setup.bash`
   - Which sets `AMENT_PREFIX_PATH=/opt/ros/jazzy`
   - Then prepends `common_ws`, giving `/common_ws:/opt/ros/jazzy`
2. Then prepends `my_robot_ws`, giving `/my_robot_ws:/common_ws:/opt/ros/jazzy`

The chain is built automatically by the nested source commands.

</details>

## Changing Search Order: The Rebuild Strategy

Sometimes you want to change the search order. For example, you've been using system Nav2, but now you want to test a custom Nav2 version that should override the system version.

**The key insight**: Search order is determined by **build-time** underlay configuration, not source-time order.

Let's say you have:
- `~/robot_ws` — Your main robot (currently uses system Nav2)
- `~/nav2_custom_ws` — Your modified Nav2 packages

Initially you built `robot_ws` with only jazzy sourced:

```bash
# Original build
source /opt/ros/jazzy/setup.bash
cd ~/robot_ws
colcon build
```

So `robot_ws` has this chain: `robot_ws → jazzy`

Now you want the chain to be: `robot_ws → nav2_custom → jazzy`

### Option 1: Rebuild robot_ws with nav2_custom_ws Sourced

The cleanest approach is to rebuild `robot_ws` with the desired underlay:

```bash
# Fresh terminal
cd ~/robot_ws
rm -rf build install log  # Clean slate

source ~/nav2_custom_ws/install/setup.bash  # Source desired underlay
colcon build --symlink-install  # Rebuild with new underlay

# Now test
source ~/robot_ws/install/setup.bash
ros2 pkg prefix nav2_controller  # Should point to nav2_custom_ws
```

Now `robot_ws/install/setup.bash` sources `nav2_custom_ws`, which sources `jazzy`.

**Pros**:
- Clean and explicit
- The workspace's setup files reflect the actual dependency chain
- No manual environment manipulation

**Cons**:
- Requires rebuild (can be slow for large workspaces)
- Changes the workspace permanently (until next rebuild)

### Option 2: Create a Separate Workspace that Overlays Both

Instead of rebuilding, create a tiny "combiner" workspace:

```bash
mkdir -p ~/test_nav2_ws/src
cd ~/test_nav2_ws

# Don't even need packages in src/, just need to build
source ~/nav2_custom_ws/install/setup.bash
source ~/robot_ws/install/setup.bash
colcon build --symlink-install  # Even with empty src/, this generates setup files

# Now use this workspace
source ~/test_nav2_ws/install/setup.bash
echo $AMENT_PREFIX_PATH
```

You'll get: `test_nav2_ws:robot_ws:nav2_custom_ws:jazzy`

Wait, that's not right! `robot_ws` is before `nav2_custom_ws`, so `robot_ws` packages will shadow `nav2_custom_ws` packages.

**This reveals a critical point**: When you source multiple workspaces before building, the **last sourced becomes the immediate underlay**. The chain is built in reverse order of sourcing.

To get the right order, source in **reverse** of desired search order:

```bash
cd ~/test_nav2_ws
rm -rf build install log

source ~/robot_ws/install/setup.bash      # Will be searched second
source ~/nav2_custom_ws/install/setup.bash  # Will be searched first (immediate underlay)
colcon build --symlink-install

source install/setup.bash
echo $AMENT_PREFIX_PATH
```

Now: `test_nav2_ws:nav2_custom_ws:robot_ws:jazzy` ← Still wrong!

Actually, this approach gets complicated because each workspace's setup file sources its own underlay chain. You end up with duplicates and unpredictable order.

**Conclusion**: Option 2 is tricky and error-prone. Stick with Option 1 (rebuild) for predictable results.

<details>
<summary><strong>Deep Dive: Why Manual Sourcing Order Gets Messy</strong></summary>

When you source multiple workspace setup files in one terminal before building, each setup file:
1. Sources its own underlay chain
2. Prepends itself to the paths

This creates overlapping and duplicated paths. For example:

```bash
source ~/workspace_a/install/setup.bash
# AMENT_PREFIX_PATH = "workspace_a:jazzy"

source ~/workspace_b/install/setup.bash  
# workspace_b sources its underlay (maybe jazzy), then prepends itself
# AMENT_PREFIX_PATH = "workspace_b:jazzy:workspace_a:jazzy"
```

Now `jazzy` appears twice, `workspace_a` is after the first `jazzy`, and the order is confusing.

The build system tries to be smart about de-duplication, but it's not always what you expect. The robust pattern: **source one workspace before build, and that becomes the underlay**.

</details>

## The local_setup.bash Alternative

Each workspace provides both `setup.bash` and `local_setup.bash`:

- **`setup.bash`**: Sources the underlay chain, then adds itself
- **`local_setup.bash`**: **Only** adds itself, doesn't source underlay

You can use `local_setup.bash` to manually construct exactly the chain you want:

```bash
# Fresh terminal
source /opt/ros/jazzy/setup.bash
source ~/nav2_custom_ws/install/local_setup.bash  # Don't re-source jazzy
source ~/robot_ws/install/local_setup.bash        # Don't re-source nav2_custom or jazzy

echo $AMENT_PREFIX_PATH
```

Result: `robot_ws:nav2_custom_ws:jazzy` (assuming proper prepending)

**Pros**:
- No rebuild required
- Full control over search order
- Good for temporary testing

**Cons**:
- Manual and error-prone
- Doesn't persist (need to repeat in each terminal)
- Can create confusing state if done wrong
- Other developers won't know about this manual setup

**Best use**: Temporary testing of different orderings. For permanent setups, use proper rebuild with underlay.

## Switching Between Configurations

Let's revisit the scenario: You want to easily switch between using system Nav2 vs. custom Nav2.

### Strategy 1: Separate Terminal Workflows

Keep different terminals for different configurations:

**Terminal 1: Using system Nav2**
```bash
source ~/robot_ws/install/setup.bash  # robot_ws built with jazzy underlay
ros2 launch my_robot_bringup robot.launch.py
```

**Terminal 2: Using custom Nav2**
```bash
source ~/robot_custom_nav_ws/install/setup.bash  # Built with nav2_custom underlay
ros2 launch my_robot_bringup robot.launch.py
```

Where `robot_custom_nav_ws` is a separate build of your robot workspace with `nav2_custom_ws` as underlay.

**Pros**: Clean separation, no confusion  
**Cons**: Maintain two copies of robot workspace

### Strategy 2: Shell Aliases

Create shell aliases for different configurations:

```bash
# Add to ~/.bashrc
alias setup-robot-standard='source ~/robot_ws/install/setup.bash'
alias setup-robot-custom-nav='source ~/robot_custom_nav_ws/install/setup.bash'
alias setup-robot-experimental='source ~/experimental_ws/install/setup.bash'
```

Then in a fresh terminal:

```bash
setup-robot-custom-nav
ros2 launch my_robot_bringup robot.launch.py
```

**Pros**: Easy to remember and type  
**Cons**: Still need multiple workspace builds

### Strategy 3: Launch File Arguments

Instead of changing workspace order, pass arguments to your launch file:

```python
def generate_launch_description():
    use_custom_nav = LaunchConfiguration('use_custom_nav')
    
    use_custom_nav_arg = DeclareLaunchArgument(
        'use_custom_nav',
        default_value='false',
        description='Use custom Nav2 implementation'
    )
    
    # Conditionally choose which nav2_bringup to include
    nav_launch = IncludeLaunchDescription(
        PythonLaunchDescriptionSource([
            PathJoinSubstitution([
                FindPackageShare(
                    PythonExpression(["'nav2_custom_bringup' if ", use_custom_nav,
                                     " else 'nav2_bringup'"])
                ),
                'launch',
                'navigation_launch.py'
            ])
        ])
    )
    
    return LaunchDescription([use_custom_nav_arg, nav_launch])
```

Launch with:
```bash
ros2 launch my_robot_bringup robot.launch.py use_custom_nav:=true
```

**Pros**: Single workspace, runtime switching  
**Cons**: Requires different package names, more complex launch files

## Best Practices for Multiple Workspaces

Based on experience, here are recommendations:

### 1. Keep Workspace Chains Simple

Prefer shallow chains:
- ✓ Good: `robot_ws → jazzy`
- ✓ Good: `robot_ws → sensors_ws → jazzy`
- ⚠ Complex: `ws_a → ws_b → ws_c → ws_d → jazzy`

Deep chains make it hard to reason about which version of packages you're using.

### 2. Use Descriptive Workspace Names

- ❌ `ws1`, `ws2`, `test_ws`
- ✓ `robot_ws`, `nav2_custom_ws`, `sensor_drivers_ws`

You'll thank yourself when debugging.

### 3. Document Your Workspace Structure

Create a README in each workspace explaining:
- Purpose of this workspace
- Expected underlay (what should be sourced before building)
- What packages it provides
- How to build it

Example `~/nav2_custom_ws/README.md`:
```markdown
# Custom Nav2 Workspace

Modified Nav2 packages for testing adaptive cruise control.

## Build Instructions
```bash
source /opt/ros/jazzy/setup.bash
colcon build --symlink-install
```

## Packages
- nav2_custom_controller — Modified DWB controller with ACC
- nav2_custom_planner — Modified Smac Planner with dynamic costs

## Using This Workspace
To use these custom Nav2 packages with your robot:
```bash
cd ~/robot_ws
rm -rf build install log
source ~/nav2_custom_ws/install/setup.bash
colcon build --symlink-install
```
```

### 4. Use Separate Workspaces for Separate Concerns

- ✓ Separate workspace for sensor drivers (stable, rarely changes)
- ✓ Separate workspace for navigation algorithms (experimental, changes often)
- ❌ Everything in one giant workspace

This allows you to:
- Rebuild only what changed
- Swap out components easily
- Share stable components across projects

### 5. Consider Version Control Implications

Each workspace should be a separate git repository. Don't create workspace chains that depend on uncommitted code:

```bash
# Bad practice
cd ~/robot_ws
source ~/experimental_ws/install/setup.bash  # experimental_ws has uncommitted changes
colcon build
git commit -m "Updated robot"  # Now robot_ws depends on uncommitted experimental code!
```

Document underlay expectations in your README.

## Matrix Testing: Testing All Combinations

Sometimes you want to test your robot code against multiple versions of dependencies. For example:
- System Nav2 vs. Custom Nav2
- Different sensor driver versions
- Different parameter sets

This is where workspace management becomes a build/test matrix problem.

### Approach: Use Scripts to Automate Rebuilds

Create a test script:

```bash
#!/bin/bash
# test_nav_variants.sh

# Test with system Nav2
echo "=== Testing with system Nav2 ==="
cd ~/robot_ws
rm -rf build install log
source /opt/ros/jazzy/setup.bash
colcon build --symlink-install
source install/setup.bash
ros2 launch my_robot_bringup robot.launch.py &  # Run in background
sleep 60  # Let it run
# ... run tests ...
killall -9 robot.launch.py

# Test with custom Nav2
echo "=== Testing with custom Nav2 ==="
cd ~/robot_ws
rm -rf build install log
source ~/nav2_custom_ws/install/setup.bash
colcon build --symlink-install
source install/setup.bash
ros2 launch my_robot_bringup robot.launch.py &
sleep 60
# ... run tests ...
killall -9 robot.launch.py

echo "Tests complete"
```

This approach:
- ✓ Ensures clean builds
- ✓ Tests actual combinations
- ✓ Can be automated in CI/CD
- ❌ Slow (full rebuilds)

<details>
<summary><strong>Deep Dive: Using Docker for Clean Environments</strong></summary>

For even cleaner testing, use Docker containers where each test starts with a completely fresh ROS 2 installation:

```dockerfile
# Dockerfile.test
FROM ros:jazzy

# Copy workspace source
COPY robot_ws/src /workspace/robot_ws/src

# Option 1: Build with system packages
RUN cd /workspace/robot_ws && \
    source /opt/ros/jazzy/setup.bash && \
    colcon build

# Entry point runs tests
CMD source /workspace/robot_ws/install/setup.bash && \
    ros2 launch my_robot_bringup test.launch.py
```

Then test different configurations:

```bash
# Test with system Nav2
docker build -f Dockerfile.test -t robot-test-system .
docker run robot-test-system

# Test with custom Nav2 (different Dockerfile that includes custom ws)
docker build -f Dockerfile.test-custom -t robot-test-custom .
docker run robot-test-custom
```

This guarantees no environment pollution between tests. It's overkill for most hobby development, but valuable for serious testing.

</details>

## Workspace Hygiene: Keeping Things Clean

Working with multiple workspaces makes it easy to create environment confusion. Here are hygiene practices:

### Clean Build Artifacts Regularly

```bash
# In each workspace
cd ~/workspace_name
rm -rf build install log
```

Do this:
- When you remove packages
- When switching between major dependency changes
- When troubleshooting weird behavior
- Periodically (weekly?) as general hygiene

### Use Separate Terminals for Separate Contexts

Don't try to switch contexts in one terminal:

```bash
# BAD: Trying to switch in same terminal
source ~/robot_ws/install/setup.bash
ros2 launch my_robot_bringup robot.launch.py
# Stop that
source ~/experimental_ws/install/setup.bash  # ← Environment now polluted
ros2 launch my_robot_bringup robot.launch.py  # ← Unpredictable results
```

Instead:

```bash
# GOOD: Fresh terminal for each context
# Terminal 1
source ~/robot_ws/install/setup.bash
ros2 launch my_robot_bringup robot.launch.py

# Terminal 2 (completely separate)
source ~/experimental_ws/install/setup.bash
ros2 launch my_robot_bringup robot.launch.py
```

### Label Your Terminals

Use terminal labels or prefixes to avoid confusion:

```bash
# In Terminal 1
export PS1="[ROBOT-STANDARD] $PS1"

# In Terminal 2
export PS1="[ROBOT-EXPERIMENTAL] $PS1"
```

Now your prompts clearly show which environment you're in.

### Check Before Running

Before running any `ros2` command, verify:

```bash
echo $AMENT_PREFIX_PATH  # Is this what you expect?
ros2 pkg prefix nav2_bringup  # Is this the right package?
```

Takes 2 seconds, saves hours of debugging.

## Summary: Multiple Workspace Patterns

Here's what to remember:

1. **Build time determines underlay**: Source desired underlay before `colcon build`
2. **Runtime just sources the top workspace**: One `source` command sources the whole chain
3. **Search order**: Last workspace sourced before build becomes first searched at runtime
4. **For temporary order changes**: Use `local_setup.bash` files
5. **For permanent setups**: Rebuild with correct underlay
6. **Keep chains shallow**: Easier to reason about
7. **Fresh terminal per context**: Don't pollute environments
8. **Document your structure**: README files save future you
